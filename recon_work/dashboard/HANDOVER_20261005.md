## 6. Verification traps that cost real time â€” reuse these

**Validating a dump.** The dump is on the *host*; `pg_restore` runs *inside* the
container. Two wrong attempts both produced a false "corrupt" verdict:

```bash
# WRONG: host path passed into the container
docker exec sgc_rent_mt_db pg_restore --list /root/backups/x.dump
# WRONG: '-' is not accepted as a filename
docker exec -i sgc_rent_mt_db pg_restore -l - < x.dump
# WRONG: /dev/stdin resolves to nothing useful
docker exec -i sgc_rent_mt_db pg_restore -l /dev/stdin < x.dump

# RIGHT: no filename at all, stdin implied -> ~16,000 TOC lines
n=$(docker exec -i sgc_rent_mt_db pg_restore -l < x.dump | wc -l)
[ "$n" -gt 1000 ] && head -c 5 x.dump | grep -q PGDMP && echo VALID
```

Do not report a tool artefact as data loss, or vice versa.

**Odoo one-off upgrades** need `--stop-after-init --no-http`. Omitting
`--no-http` fails with `OSError: [Errno 98] Address already in use`.

### Two Odoo 19 traps hit while building this

- **`<group expand="0" ...>` is invalid in an Odoo 19 `search` view.** The RNG
  allows `field|group|separator|filter|newline|searchpanel`, but `group`
  rejects `expand`. Every working search view in this repo avoids `<group>`
  entirely and uses plain group-by filters (`context="{'group_by': 'x'}"`).
  Match that. This caused one failed upgrade; it rolled back cleanly and the
  module stayed at 2.67.
- **`arch_db` is `jsonb` in Odoo 19, not text.** `length(arch_db)` fails; use
  `length(arch_db::text)`. Likewise many `ir_*` columns are jsonb, so
  `coalesce(name,'?')` raises `invalid input syntax for type json`. Cast:
  `coalesce(name::text,'?')`.

Validate arches with Odoo's own validator instead of guessing, run from inside
the container (it has lxml and `odoo.tools.view_validation`). The arch is a
child **element** of `<field name="arch">`, not `.text`:

```bash
docker exec -i sgc_rent_mt python3 - /mnt/extra-addons/<module>/<file>.xml <<'PYEOF'
import sys
from lxml import etree
from odoo.tools import view_validation
t = etree.parse(sys.argv[1])
for rec in t.findall('.//record[@model="ir.ui.view"]'):
    el = [c for c in rec.find('field[@name="arch"]') if isinstance(c.tag, str)][0]
    view_validation.validate(etree.tostring(el, encoding='unicode'), el.tag)
    print("OK", rec.get('id'), el.tag)
PYEOF
```

The client-facing call is `model.get_view(view_type='form')`. `ir.ui.view._get_view`
is internal and will iterate a model-name string character by character if you
pass it one, raising `Expected singleton`.

### 12.1 FIXED: the client action registered three times, one of them falsely

`static/src/js/property_dashboard_register.js` guarded its registration with

```js
try {
    actions.get("property_dashboard");
    console.log('[rental_property_dashboard] Already registered');
} catch {
    actions.add("property_dashboard", RentalPropertyDashboard);   // unreachable
}
```

**`Category.get()` returns `undefined` for a missing key; it does not throw**
(`odoo/addons/web/static/src/core/registry.js`). So the `catch` never ran, the
`add()` inside it was dead code, and the console printed a false "Already
registered" on a cold first load. The action worked only because
`static/src/components/rental_property_dashboard.js` also called `actions.add()`
at import time.

Fixed by making the component the single authoritative registration point using
the real API, `Category.contains()`:

```js
const dashboardActions = registry.category("actions");
if (dashboardActions.contains("property_dashboard")) { ... } else { dashboardActions.add(...); }
```

Deleted two dead files: `property_dashboard_register.js` (removed from the
manifest `assets` too) and `rental_management_init.js` (never referenced
anywhere; it also imported a non-existent `@rental_management/...` path).

**Lesson: verify registry/ORM API semantics in the source before writing a guard
around them.** A `try/catch` used as an existence check is a silent no-op when the
API returns a falsy value instead of raising.

### 12.2 FIXED: a patch that swallowed every error

`static/src/js/list_renderer_fix.js` wraps the patched

### 12.3 NOT FIXED: the document.write violation is Odoo core, and it is safe

```
[Violation] Avoid using document.write()
```

Source: `odoo/addons/web/static/src/views/fields/iframe_wrapper/iframe_wrapper_field.js`.
Core's own comment says *"The document.write is not recommended ... Therefore,
document.write makes it much more trivial in our situation."*

Why it was left alone:

- It writes to `this.iframeRef.el.contentDocument` - **an iframe's** document,
  not the main page. The failure mode that makes `document.write` dangerous
  (Chrome destroying the whole page load on a slow connection) applies to the
  *parser-blocking main document* write, not this.
- The `iframe_wrapper` widget is used by exactly one view in the whole system:
  `web.view_base_document_layout` (model `base.document.layout`). **No view in
  this codebase uses it.** Our `description` fields are `widget="html"`.
- Silencing it would mean monkey-patching an Odoo core component from this addon:
  no functional gain, and it would have to be re-validated on every Odoo upgrade.

### 12.4 Asset bundles do NOT rebuild on module upgrade

This bit and is worth knowing: after upgrading to 19.0.2.71 the browser was
**still being served the old JavaScript**. `ir_attachment` row
`web.assets_web.min.js` (id 4432) was still dated 2026-10-04, and fetching its
URL over HTTP proved the old strings were still in it (`Already registered`
present, `client action registered` absent).

Odoo caches a compiled bundle in `ir_attachment` keyed by bundle name and only
rebuilds it when something invalidates the cache. The fix is to delete the cached
rows; the next request recompiles from source:

```sql
DELETE FROM ir_attachment WHERE name LIKE 'web.assets_web.%' AND url IS NOT NULL;
```

These are build artefacts, so this is safe. **After any change to files under
